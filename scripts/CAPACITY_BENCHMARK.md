# Capacity benchmark

Run from the project root, with its existing Node/tsx dependencies installed:

```sh
./node_modules/.bin/tsx scripts/capacity-benchmark.ts \
  --clients=5,10,20,30 --speed=4 --seconds=30 --start-tick=300 \
  --label=candidate --output=output/capacity/candidate-4x.json
```

`--target=/absolute/path/to/checkout` selects another checkout, so the same harness
can measure an archived baseline and the candidate. Each target must have its own
dependencies available. `--transport=auto` uses that target's shared sync decoder
if it exists. `--transport=full` explicitly requests full snapshots for a transport
comparison; `--transport=sync` fails if the target does not support the protocol.

For a 30-second run at 12x speed, start at tick 60 so an adequately performing
market remains intraday throughout the measurement:

```sh
./node_modules/.bin/tsx scripts/capacity-benchmark.ts \
  --clients=3,5,10 --speed=12 --seconds=30 --start-tick=60 \
  --output=output/capacity/candidate-12x.json
```

The default 4x fixture starts at tick 300. It is a real deterministic market
generated by `createMarket(26783)` and 300 one-second engine steps. It has substantial
accumulated trade/history data. At 4x speed it reaches approximately tick 420 after
30 seconds, before the natural pause at tick 450. The 12x run has a lighter opening
fixture and should be described separately. For a heavier 12x stress run, use tick
300; the harness will explicitly advance and resume the next day after closing,
counting those actions separately. Its result includes the nightly transition cost.

Every stage creates independent synthetic saves and fresh session tokens in a
random temporary directory. It starts a separate application process on a loopback
ephemeral port. It never connects to a supplied public server or opens production
save files. The generated save directory is removed after graceful server shutdown.
Neither the parent nor the child modifies any game source.

The load generator uses actual HTTP requests, keeps one request in flight per
client, advertises gzip/deflate/Brotli support, applies full/delta snapshots, and
polls every 1.2 seconds. Overdue slots are skipped and reported. Startup loading and
unpause actions are excluded from steady-state timing. The benchmark currently
models players watching an advancing market, plus explicit next-day/resume actions
if needed. Add `--trade-every-ms=5000` to make every client submit a small order
approximately every five seconds, beginning five seconds into the measured run:

```sh
./node_modules/.bin/tsx scripts/capacity-benchmark.ts \
  --clients=5,10 --speed=4 --seconds=30 --start-tick=300 \
  --trade-every-ms=5000 --label=candidate-mixed \
  --output=output/capacity/candidate-mixed-4x.json
```

The mixed workload uses valid 100-share marketable limit orders: sell ordinary
shares when an available T+1 holding and bid exist, otherwise buy when an ask and
sufficient cash exist. A day-one fixture normally buys only because today's
purchases cannot be sold yet. It rotates stocks, avoids crossing the player's own
opposite orders, and skips a trading slot when the current phase/cash/holdings do
not permit an order. Acceptance is measured; immediate execution is not guaranteed.
Trading and polling have independent deadlines but remain serialized per client,
so their snapshot versions cannot race. Slow actions can consume poll slots, which
are counted as missed rather than hidden by slowing the configured poll cadence.
The default `--trade-every-ms=0` disables this workload.

JSON reports `trading` attempts/acceptances/rejections/errors, buy/sell counts,
skipped/missed trade slots and separate action/trade latency distributions;
`rawTradeOutcomes` includes HTTP status and the application's result. HTTP 422
business rejections (for example, a phase transition between snapshot and order)
are counted separately and do not trip the transport/server error stop threshold.
`totalRequestsPerSecond` and `responseWireMbps` include actions. A 60-second 4x run
starting at tick 300 crosses closing and includes explicit next-day work; choose
`--start-tick=180` to remain intraday for a 60-second 4x run, while accepting its
lighter initial fixture. Keep the fixture identical when comparing baseline and
candidate.

The test does not model browser rendering, public network latency, TLS, proxy load,
or simultaneous first visits.

Raw JSON contains each request's latency, wire and decoded body bytes, errors,
per-client simulation progress, polling attainment, and approximately one-second
application CPU/RSS/event-loop samples. CPU percentages are relative to one core:
100% means one fully busy CPU core. Parent load-generator CPU is also reported;
both processes compete for the host's resources. The wire-byte count excludes
HTTP headers/TCP/TLS. Compression performed only by an external reverse proxy is
not present in these loopback measurements.

Simulation progress uses `phaseProgress` and phase durations. It never uses
`revision`, which also increments on market events. Progress ratios are computed
between each client's first and last observed snapshot and can deviate slightly
from 1 because simulation steps are discrete. The 150 simulated seconds skipped by
an explicit overnight transition are excluded from active progress.

By default further client levels stop after a stage with p95 latency over 5 seconds,
minimum simulation progress below 50%, polling attainment below 50%, or the live
error threshold. `--stop-p95-ms=...` adjusts latency; `--continue-after-saturation`
continues later levels deliberately. Each HTTP request has a 12-second deadline
(`--timeout-ms=...`). A child that cannot shut down within 15 seconds is terminated.
These are protective stop thresholds, not criteria for calling a game smooth.
Assess capacity using latency, achieved simulation speed and polling together;
zero HTTP errors alone is insufficient.

Use the same seed, start tick, speed, duration, client counts and host for a baseline
comparison. Run stages sequentially, and leave resource headroom for real users.
Keep the raw output file and its source revision alongside any reported conclusion.
